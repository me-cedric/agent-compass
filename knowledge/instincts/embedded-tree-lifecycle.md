# Give every embedded tree a lifecycle row

## The four questions every row answers

Trees that sit side by side look alike and behave differently. Write one table
that answers four questions per tree:

| Tree | Who generates it | Who consumes it | When it refreshes | What breaks on drift |
| --- | --- | --- | --- | --- |
| `resources/<corpus>/` | `vendor-<corpus>` script | copied out at provisioning time | on an upstream bump, by re-running the script | the package ships stale content, silently |
| `resources/<own>/` | edited by hand in this repository | same reader | with the feature that needs it | the reader finds a missing item |
| `<compiled>/` | edited by hand in this repository | compiled into the binary | at build time | the build fails |

The fourth column earns the table. A resource list kept in two build scripts
drifted in both, and a packaged archive shipped without one whole tree. Nobody
noticed, because a missing resource produces an empty screen and no error.

Keep the table next to the trees it describes, not in a distant document.

## Choose compile-in or ship-as-resource on purpose

The same file has two possible fates, and the failure mode is the difference:

- **Compiled into the binary** (an embed macro or a bundler import). A missing
  file is a **build** error. The content cannot drift from the code that reads
  it, and nobody can patch it. It grows the binary and it is invisible on disk.
- **Shipped as a packaged resource.** The file stays readable and patchable, and
  a support engineer can inspect it. A missing file is a **runtime** error,
  found at the moment a user needs the feature.

Compile in the content the application cannot start without, and that changes
only with a release: parsers, prompts, embedded templates the application itself
executes.

Ship as a resource the content that leaves the application — anything copied into
another repository, read by a person, or regenerated by a vendoring script. Then
resolve it through one helper that tries every layout the packaging produces: a
development run and a packaged run rarely put the resource directory in the same
place.

Whichever fate you pick, keep the single declaration and the drift gate from
sections 1 and 2. One list, one reader, one check.
